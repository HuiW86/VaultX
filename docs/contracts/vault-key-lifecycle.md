# Vault Key Lifecycle Contract

Version 2.3 (2026-09-28). Status: **2.2 confirmed; 2.3 changes drafted by the implementer, pending owner confirmation.** 2.3 adds C13, rewrites the C11 decision (first recovery kit at setup, no close path while a kit is being generated) and the migration commit decision (source row counts persisted at the commit and required by every deletion of the legacy DB; manual-restore error instead of opening an incomplete DB), corrects the E4 rationale, records E8 and adds the manual restore procedure. **None of the 2.3 changes is owner-confirmed yet.** They fix the two known inaccuracies the owner recorded when confirming 2.2 (E4 rationale overstated G2 for row-loss corruption; the C11 decision claimed the setup wizard shows the first kit, which the app did not). 2.2 (confirmed by the owner on 2026-09-28, including exceptions E4–E7) tightened the check before the legacy DB is deleted (G2), guarded closing the new-kit dialog (G1) and recorded exceptions E4–E7. 2.1 (drafted by the implementer in 3acd08b, confirmed by the owner on 2026-09-28) added C10–C12, tightened the migration commit (F1) and Keychain invalidation (F4) decisions and recorded exceptions E1–E3 after the DEK/KEK review (owner: project owner). Supersedes v1 (same date), which assumed the password-derived key encrypted the DB and fields directly; that design lost field data on recovery (fields stayed encrypted with the old key).

This file is the authoritative source for how the vault data key, key-encryption keys, KDF salt, recovery kit and Keychain copy change together. Code must follow it; to change behavior described here, update this file first (or in the same commit) and keep the checks below passing.

Scope: `src-tauri/src/commands/{auth,recovery,security,entries}.rs`, `src-tauri/src/db/`, `src-tauri/src/crypto/`, frontend stores cleared after recovery. Any flow that creates, unlocks, migrates, recovers or changes the credentials of a vault is in scope.

## Key hierarchy

- **DEK** (data encryption key): 32 random bytes generated once per vault. It is the SQLCipher key **and** the AES-256-GCM field key. It never changes on password change or recovery. (Full key rotation is a separate, future operation.)
- **Password KEK**: Argon2id(password, salt). Only wraps the DEK.
- **Recovery KEK**: derived from the recovery key. Only wraps the DEK.
- Wrapping uses AES-256-GCM with a purpose label bound as associated data (e.g. `vaultx:dek:password`, `vaultx:dek:recovery`) so one wrap cannot be substituted for another.
- `.vaultx-meta` version 2 holds: KDF params + salt, `dek_wrapped_by_password`, optional `dek_wrapped_by_recovery` (replaces `recovery_blob`). Version 1 meta (no wrapped DEK) is a legacy vault and must be migrated (C8).

## Conventions

| ID | Convention (target behavior) | Coverage | Check |
|---|---|---|---|
| C1 | If any step of a credential-changing or migration flow fails or the process crashes at any point, **at least one previously valid credential (old password, new password, or recovery key) still opens the vault with all data readable** (C7). A state where no credential works is forbidden. | recovery, password change, v1→v2 migration | Fault-injection tests at every commit point, including simulated restart |
| C2 | The DB and all encrypted fields use the DEK. Password change and recovery only rewrap the DEK and atomically rewrite meta; they **never** rekey the DB or re-encrypt fields. | recovery, password change | Test: DB file bytes unchanged by recovery; fields readable after |
| C3 | `.vaultx-meta` (and any pending/marker file) is written atomically (temp file + rename). | all meta writes | Existing behavior; do not regress |
| C4 | Error messages never contain keys, salts, passwords or recovery key characters; key material (DEK, KEKs, raw recovery key, hex key strings) stays in `Zeroizing`. | all flows | Review + tests asserting error strings |
| C5 | After a successful recovery, the recovery kit used is invalidated (`dek_wrapped_by_recovery` removed); the user must generate a new kit. On failure the old kit keeps working. | recovery | Success-path and failure-path tests |
| C6 | Keychain (Touch ID) stores a copy of the DEK, never a password KEK. After a successful recovery, the Keychain item is deleted and `touch_id_enabled` set to false; if deletion fails the command reports it explicitly (not silent success). Keychain calls sit behind a function that tests can replace. | recovery, Touch ID setup/unlock | Test with a fake Keychain |
| C7 | After create, unlock, migration, recovery or password change, **all data is readable**: every sensitive field type (`password`, `hidden`, `card_number`), all `password_history` values, and trashed entries. "The DB opens" is not sufficient evidence. | all flows | Tests decrypt every field and history row |
| C8 | A v1 vault is migrated to v2 on first successful password unlock: export to a shadow DB keyed with a new random DEK (e.g. `sqlcipher_export`), re-encrypt all fields and history in the shadow, verify every value decrypts and the shadow reopens, then commit through explicit, restart-safe states; the original DB is kept until the commit completes. | v1 vaults | Migration tests incl. fault injection at each state |
| C9 | After a successful recovery the frontend clears decrypted entry and search caches. | frontend | Review |
| C10 | Every flow that creates, renames or deletes vault files (create, password/Touch ID unlock incl. `reconcile` and migration, Touch ID enable, recovery kit generation, recovery, password change, Keychain invalidation) holds a **cross-process exclusive lock** for its whole duration, so two VaultX processes never interleave these steps. Before deleting a superseded DB the flow re-confirms, under the lock, that the new DB opens with the DEK. | all flows | Tests: concurrent reconcile during migration cannot remove the shadow; flows wait for a held lock |
| C11 | A vault without a usable recovery kit is **visible to the user**: after unlock, if meta has no recovery wrap (v2 without `dek_wrapped_by_recovery`), the UI shows a notice with a regenerate action. Settings always offers "Regenerate recovery kit" (same `generate_recovery_kit` command and download as setup; the previous kit stops working). All texts exist in `en` and `zh-CN`. | recovery, migration, frontend | Vitest: notice shown/hidden by status; regenerate calls the command and offers the download; `<App/>` new-vault flow shows the first kit and keeps the main window hidden until the download (2.3); no close path while a kit is being generated (2.3) |
| C13 | While the legacy `vault.db` superseded by a committed migration still exists, it is deleted **only** when `vault.v2.db` passes verification with exactly the source row counts recorded in meta at the migration commit, on every deleting path. If `vault.v2.db` fails verification in that state, no flow opens it or commits anything onto it: password unlock, Touch ID unlock and recovery return `manual_restore_required`, and the UI explains the manual restore in `en` and `zh-CN`. (Drafted in 2.3, pending owner confirmation.) | migration, unlock, Touch ID, recovery, frontend | Tests: rows dropped from the new DB after the commit keep the legacy DB via password unlock, Touch ID retry, v1 and v2 recovery; vitest: notice shown for each path |
| C12 | Recovery input is bounded and rate-limited like password unlock: the recovery key text is rejected above `MAX_RECOVERY_KEY_INPUT_LEN` bytes before parsing; failed recovery attempts (invalid key) use the **same persistent failed-attempt counter and delay schedule** as password unlock, a rate-limited attempt does not evaluate the key, and success clears the counter. | recovery | Tests: long input rejected; lockout after repeated failures blocks even a valid key; shared counter |

## Implementation decisions (2026-09-28, recorded with the v2 implementation)

These refine how the conventions above are met; they do not relax any of them.

- **Code location.** Flows live in `src-tauri/src/vault/` (`lifecycle.rs`: create, unlock, Touch ID, recovery kit, recovery, password change, Keychain invalidation, `reconcile`; `migration.rs`: v1→v2; `keystore.rs`: `KeyStore` trait + in-memory fake; `recovery_key.rs`). Wrapping is `crypto/key_wrap.rs`. Tauri commands only call these. Every flow takes a fault hook called at each commit point; production passes `no_faults`.
- **Meta.** `.vaultx-meta` v2 also carries `db_path` (one of `vault.db`, `vault.v2.db`; anything else is rejected) and `keychain_invalidation_pending`. Meta writes are temp file + fsync + rename + directory fsync (C3). A failing directory fsync is an error returned to the caller (`sync_dir` no longer swallows it); no destructive step may follow it.
- **Migration commit (C8, C13).** The shadow DB is `vault.v2.db`; its file and directory entry are fsynced before the commit. The single commit point is the atomic rename of a v2 meta whose `db_path` is `vault.v2.db`, followed by a directory fsync that must succeed. That meta also carries `superseded_db`: the source DB's row counts (vaults, entries, trashed entries, fields, password_history), plus the v1 KDF config (salt) and `recovery_blob` needed for a manual restore of the legacy DB (see below). Before the commit, the v1 meta and `vault.db` are untouched. After it, `vault.db` is deleted **only** by `migration::remove_superseded_db` (under the C10 lock), which every deleting path uses: the migration itself, password unlock, Touch ID unlock and v2 recovery. It requires that the on-disk meta is v2 referencing `vault.v2.db`, that this DB opens with the DEK **and passes `migration::verify_migrated_db` with exactly the recorded counts** (tables `vaults`, `entries`, `fields`, `password_history` present, `PRAGMA quick_check` = ok, every sensitive field and history value decrypting with the DEK), and that the directory syncs. "Opens" alone is not evidence (a 0-byte file opens with any key), and neither is "schema intact and at least one vault" (rows can be lost with a valid schema). Afterwards the marker is cleared. Meta written by 2.2 code has no recorded counts: its legacy DB is kept (only logged) and the new DB must still pass the structural checks and contain a vault row. If the verification fails while `vault.db` exists, the flow does not open the vault: password unlock returns `UnlockFailure::ManualRestoreRequired` (IPC kind `manual_restore_required`, not counted as a failed attempt), Touch ID unlock returns the error `manual_restore_required`, v2 recovery returns `RecoverFailure::ManualRestoreRequired` **before** its commit (the kit keeps working), and a v1 recovery whose migration committed but did not verify returns the same error (read-only check, nothing deleted); `LockScreen` shows the `lock.manual_restore_*` notice. Any other doubt (sync error, file not deletable, no recorded counts) keeps `vault.db`, is logged and the next keyed open retries. `reconcile` (run at the start of every flow, under the lock) deletes a stale `.vaultx-meta.tmp` and any known DB file the current meta does not reference, only if the referenced DB exists, **except** the legacy `vault.db` superseded by `vault.v2.db`, which it never deletes because it has no key to verify the new DB.
- **Manual restore (E4, C13).** When the app reports `manual_restore_required`, `vault.db` is the complete pre-migration vault, keyed with the v1 key = Argon2id(old password, `superseded_db.legacy_kdf.salt`) (or recoverable with the old v1 kit via `superseded_db.legacy_recovery_blob`). Procedure (support-assisted; no in-app tool yet): quit VaultX, copy the whole data directory, then replace `.vaultx-meta` with a v1 meta (`version` 1, `kdf` = `superseded_db.legacy_kdf`, the original `created_at`, `db_path` `vault.db`, `recovery_blob` = `superseded_db.legacy_recovery_blob`) and move `vault.v2.db` aside; the next password unlock migrates again. Nothing is deleted automatically in this state.
- **Migration failure (C1 over C8).** If migration fails during a password unlock, the unlock still succeeds on the v1 vault ("legacy mode") and migration is retried at the next password unlock. In legacy mode, generating a recovery kit and enabling Touch ID are refused so the legacy key is never persisted again. Touch ID unlock is refused for v1 vaults.
- **v1 recovery.** Recovering a v1 vault decrypts the legacy key from `recovery_blob` and runs the same migration with the new password; the resulting v2 meta has no recovery wrap (C5).
- **Keychain invalidation (C6).** Recovery and migration set `keychain_invalidation_pending` in the same atomic meta write that commits them. Afterwards (and on every later password unlock while the flag is set) the app attempts both steps independently, setting `touch_id_enabled` to false and deleting the Keychain item (a settings failure never skips the deletion; both errors are reported), and clears the flag only when both succeeded. Touch ID unlock is refused while the flag is set. If deletion fails after a recovery, `recover_with_key` returns `touch_id_cleanup_failed: true` and the UI shows an error toast.
- **Cross-process lock (C10).** `vault::lock::VaultLock`: BSD `flock(2)` (declared against the C library, no new crate) on `<data dir>/.vaultx-lock`. The kernel drops it when the holder exits or crashes, so there is no stale-lock state. Public flows acquire it once (waiting up to 30 s, then failing with a "vault is busy" error and no changes) and call `*_locked` internals, which take `&VaultLock` as proof; it is never nested. `lifecycle::recovery_kit_status` only reads meta and takes no lock. On non-unix targets (not shipped; the app is macOS-only) the lock is a no-op. The lock covers lifecycle flows only; it does not stop a second process that already has the DB open from writing entries through SQLite; whether to enforce a single running instance is an open question for the owner.
- **Recovery kit notice (C11).** `get_recovery_kit_status` returns `{ present, can_generate }`; `present` is true for v2 with `dek_wrapped_by_recovery` or v1 with `recovery_blob`; `can_generate` is false in legacy mode. The frontend shows the missing-kit banner when `!present && can_generate` and refreshes the status after unlock, recovery and regeneration. Once "generate" has been clicked and until `generate_recovery_kit` returns, the dialog cannot be closed at all (X, overlay, Escape and "Cancel" are disabled, `Modal dismissible={false}`), for both the banner and the Settings entry, because the backend may already have committed the new kit. Once a new kit has been generated the previous one no longer works, so until the user downloads it the dialog's close paths (X, overlay click, Escape) do not close it silently: they show a confirmation stating that the previous kit no longer works, whose own close paths return to the key; only the explicit "Close anyway" button closes it (`RecoveryKitDialog`). **First kit at setup.** After `setup_vault` succeeds the app enters status `setup_recovery`, not `unlocked`: `App` keeps rendering the same `SetupWizard` (the main window is not mounted), which generates the first kit through an explicit action (automatically once after creation, then a retry button if it fails) and shows it as a full page with no close path; "I've saved my recovery kit" stays disabled until the download, and only then does "Get started" switch to `unlocked`. A "first kit pending" flag (webview `localStorage`, set at creation, cleared on download) sends a later unlock (password or Touch ID) or a reload of the unlocked window back to this kit step, so a restart, quit or lock before the download still ends at the kit page, where a new kit is generated (the unseen one stops working). The activity heartbeat also runs during `setup_recovery` so auto-lock does not interrupt the kit page.
- **Recovery rate limit (C12).** `MAX_RECOVERY_KEY_INPUT_LEN` = 64 bytes (a kit key is 32 characters). The counter lives in `.vaultx-failed-attempts` (`vault::rate_limit`), shared with password unlock: 1–4 failures no delay, then 5 s, 15 s, 30 s, 60 s. A rate-limited recovery returns "Too many failed attempts. Wait N seconds." without reading meta or deriving keys.
- **Password change.** No IPC command or UI exists yet; `vault::lifecycle::change_password` is the only implementation and is covered by the C1/C2 tests. Any future command must call it.

## Reporting and arbitration

Any change in scope must report the status of **every** convention above: satisfied (with test or code location), or an exception recorded in this file with scope, reason and date. Skipping a convention silently is a violation. If code and this contract disagree, fix the code unless the owner changes the contract.
