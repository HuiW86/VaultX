# Vault Key Lifecycle Contract

Version 2.1 (2026-09-28). Status: **confirmed** (owner: project owner). 2.1 adds C10–C12, tightens the migration commit (F1) and Keychain invalidation (F4) decisions and records exceptions E1–E3 after the DEK/KEK review. Supersedes v1 (same date), which assumed the password-derived key encrypted the DB and fields directly; that design lost field data on recovery (fields stayed encrypted with the old key).

This file is the authoritative source for how the vault data key, key-encryption keys, KDF salt, recovery kit and Keychain copy change together. Code must follow it; to change behavior described here, update this file first (or in the same commit) and keep the checks below passing.

Scope: `src-tauri/src/commands/{auth,recovery,security,entries}.rs`, `src-tauri/src/db/`, `src-tauri/src/crypto/`, frontend stores cleared after recovery. Any flow that creates, unlocks, migrates, recovers or changes the credentials of a vault is in scope.

## Key hierarchy

- **DEK** (data encryption key): 32 random bytes generated once per vault. It is the SQLCipher key **and** the AES-256-GCM field key. It never changes on password change or recovery. (Full key rotation is a separate, future operation.)
- **Password KEK**: Argon2id(password, salt). Only wraps the DEK.
- **Recovery KEK**: derived from the recovery key. Only wraps the DEK.
- Wrapping uses AES-256-GCM with a purpose label bound as associated data (e.g. `vaultx:dek:password`, `vaultx:dek:recovery`) so one wrap cannot be substituted for another.
- `.vaultx-meta` version 2 holds: KDF params + salt, `dek_wrapped_by_password`, optional `dek_wrapped_by_recovery` (replaces `recovery_blob`). Version 1 meta (no wrapped DEK) is a legacy vault and must be migrated (C8).

## Conventions

| ID | Convention (target behavior) | Coverage | Check |
|---|---|---|---|
| C1 | If any step of a credential-changing or migration flow fails or the process crashes at any point, **at least one previously valid credential (old password, new password, or recovery key) still opens the vault with all data readable** (C7). A state where no credential works is forbidden. | recovery, password change, v1→v2 migration | Fault-injection tests at every commit point, including simulated restart |
| C2 | The DB and all encrypted fields use the DEK. Password change and recovery only rewrap the DEK and atomically rewrite meta; they **never** rekey the DB or re-encrypt fields. | recovery, password change | Test: DB file bytes unchanged by recovery; fields readable after |
| C3 | `.vaultx-meta` (and any pending/marker file) is written atomically (temp file + rename). | all meta writes | Existing behavior; do not regress |
| C4 | Error messages never contain keys, salts, passwords or recovery key characters; key material (DEK, KEKs, raw recovery key, hex key strings) stays in `Zeroizing`. | all flows | Review + tests asserting error strings |
| C5 | After a successful recovery, the recovery kit used is invalidated (`dek_wrapped_by_recovery` removed); the user must generate a new kit. On failure the old kit keeps working. | recovery | Success-path and failure-path tests |
| C6 | Keychain (Touch ID) stores a copy of the DEK, never a password KEK. After a successful recovery, the Keychain item is deleted and `touch_id_enabled` set to false; if deletion fails the command reports it explicitly (not silent success). Keychain calls sit behind a function that tests can replace. | recovery, Touch ID setup/unlock | Test with a fake Keychain |
| C7 | After create, unlock, migration, recovery or password change, **all data is readable**: every sensitive field type (`password`, `hidden`, `card_number`), all `password_history` values, and trashed entries. "The DB opens" is not sufficient evidence. | all flows | Tests decrypt every field and history row |
| C8 | A v1 vault is migrated to v2 on first successful password unlock: export to a shadow DB keyed with a new random DEK (e.g. `sqlcipher_export`), re-encrypt all fields and history in the shadow, verify every value decrypts and the shadow reopens, then commit through explicit, restart-safe states; the original DB is kept until the commit completes. | v1 vaults | Migration tests incl. fault injection at each state |
| C9 | After a successful recovery the frontend clears decrypted entry and search caches. | frontend | Review |
| C10 | Every flow that creates, renames or deletes vault files (create, password/Touch ID unlock incl. `reconcile` and migration, Touch ID enable, recovery kit generation, recovery, password change, Keychain invalidation) holds a **cross-process exclusive lock** for its whole duration, so two VaultX processes never interleave these steps. Before deleting a superseded DB the flow re-confirms, under the lock, that the new DB opens with the DEK. | all flows | Tests: concurrent reconcile during migration cannot remove the shadow; flows wait for a held lock |
| C11 | A vault without a usable recovery kit is **visible to the user**: after unlock, if meta has no recovery wrap (v2 without `dek_wrapped_by_recovery`), the UI shows a notice with a regenerate action. Settings always offers "Regenerate recovery kit" (same `generate_recovery_kit` command and download as setup; the previous kit stops working). All texts exist in `en` and `zh-CN`. | recovery, migration, frontend | Vitest: notice shown/hidden by status; regenerate calls the command and offers the download |
| C12 | Recovery input is bounded and rate-limited like password unlock: the recovery key text is rejected above `MAX_RECOVERY_KEY_INPUT_LEN` characters before parsing; failed recovery attempts (invalid key) use the **same persistent failed-attempt counter and delay schedule** as password unlock, a rate-limited attempt does not evaluate the key, and success clears the counter. | recovery | Tests: long input rejected; lockout after repeated failures blocks even a valid key; shared counter |

## Implementation decisions (2026-09-28, recorded with the v2 implementation)

These refine how the conventions above are met; they do not relax any of them.

- **Code location.** Flows live in `src-tauri/src/vault/` (`lifecycle.rs`: create, unlock, Touch ID, recovery kit, recovery, password change, Keychain invalidation, `reconcile`; `migration.rs`: v1→v2; `keystore.rs`: `KeyStore` trait + in-memory fake; `recovery_key.rs`). Wrapping is `crypto/key_wrap.rs`. Tauri commands only call these. Every flow takes a fault hook called at each commit point; production passes `no_faults`.
- **Meta.** `.vaultx-meta` v2 also carries `db_path` (one of `vault.db`, `vault.v2.db`; anything else is rejected) and `keychain_invalidation_pending`. Meta writes are temp file + fsync + rename + directory fsync (C3). A failing directory fsync is an error returned to the caller (`sync_dir` no longer swallows it); no destructive step may follow it.
- **Migration commit (C8).** The shadow DB is `vault.v2.db`; its file and directory entry are fsynced before the commit. The single commit point is the atomic rename of a v2 meta whose `db_path` is `vault.v2.db`, followed by a directory fsync that must succeed. Before it, the v1 meta and `vault.db` are untouched. After it, `vault.db` is deleted **only** once the directory syncs, the on-disk meta is re-read as v2 referencing `vault.v2.db`, and that DB opens with the DEK (`migration::remove_superseded_db`, under the C10 lock); otherwise `vault.db` is kept and the next keyed open (password unlock, Touch ID unlock, recovery) retries. `reconcile` (run at the start of every flow, under the lock) deletes a stale `.vaultx-meta.tmp` and any known DB file the current meta does not reference, only if the referenced DB exists, **except** the legacy `vault.db` superseded by `vault.v2.db`, which it never deletes because it has no key to verify the new DB.
- **Migration failure (C1 over C8).** If migration fails during a password unlock, the unlock still succeeds on the v1 vault ("legacy mode") and migration is retried at the next password unlock. In legacy mode, generating a recovery kit and enabling Touch ID are refused so the legacy key is never persisted again. Touch ID unlock is refused for v1 vaults.
- **v1 recovery.** Recovering a v1 vault decrypts the legacy key from `recovery_blob` and runs the same migration with the new password; the resulting v2 meta has no recovery wrap (C5).
- **Keychain invalidation (C6).** Recovery and migration set `keychain_invalidation_pending` in the same atomic meta write that commits them. Afterwards (and on every later password unlock while the flag is set) the app attempts both steps independently, setting `touch_id_enabled` to false and deleting the Keychain item (a settings failure never skips the deletion; both errors are reported), and clears the flag only when both succeeded. Touch ID unlock is refused while the flag is set. If deletion fails after a recovery, `recover_with_key` returns `touch_id_cleanup_failed: true` and the UI shows an error toast.
- **Cross-process lock (C10).** `vault::lock::VaultLock`: BSD `flock(2)` (declared against the C library, no new crate) on `<data dir>/.vaultx-lock`. The kernel drops it when the holder exits or crashes, so there is no stale-lock state. Public flows acquire it once (waiting up to 30 s, then failing with a "vault is busy" error and no changes) and call `*_locked` internals, which take `&VaultLock` as proof; it is never nested. `lifecycle::recovery_kit_status` only reads meta and takes no lock. On non-unix targets (not shipped; the app is macOS-only) the lock is a no-op. The lock covers lifecycle flows only; it does not stop a second process that already has the DB open from writing entries through SQLite; whether to enforce a single running instance is an open question for the owner.
- **Recovery kit notice (C11).** `get_recovery_kit_status` returns `{ present, can_generate }`; `present` is true for v2 with `dek_wrapped_by_recovery` or v1 with `recovery_blob`; `can_generate` is false in legacy mode. The frontend shows the missing-kit banner when `!present && can_generate` and refreshes the status after unlock, recovery and regeneration.
- **Recovery rate limit (C12).** `MAX_RECOVERY_KEY_INPUT_LEN` = 64 characters (a kit key is 32). The counter lives in `.vaultx-failed-attempts` (`vault::rate_limit`), shared with password unlock: 1–4 failures no delay, then 5 s, 15 s, 30 s, 60 s. A rate-limited recovery returns "Too many failed attempts. Wait N seconds." without reading meta or deriving keys.
- **Password change.** No IPC command or UI exists yet; `vault::lifecycle::change_password` is the only implementation and is covered by the C1/C2 tests. Any future command must call it.

## Recorded exceptions

Known gaps accepted for now. Each names its scope, reason and date; removing one requires a fix plus the matching test.

| ID | Convention | Scope | Reason | Date |
|---|---|---|---|---|
| E1 (P3) | C4 | The recovery key in text form is not zeroized: the intermediate `String`s in `recovery_key::encode_grouped`, `RecoveryKitResult.recovery_key` / `file_content`, and the kit file content, plus their copies across IPC and in the webview. | The text must cross IPC to be shown and downloaded, where it cannot be zeroized anyway; the raw key bytes and the KEK stay in `Zeroizing`. Low marginal value versus the refactor. | 2026-09-28 |
| E2 (P3) | error reporting (C1 diagnostics) | `lifecycle::unlock_with_password`, v1 branch: any `open_db` failure with the legacy key (I/O error, corrupted DB, missing file) is reported as `WrongCredential` ("Incorrect master password") and counted toward the rate limit. | v1 cannot distinguish a wrong key from a corrupted file with SQLCipher alone; the v1 path is transitional. No data is modified. | 2026-09-28 |
| E3 (P2) | C7 / C8 | Vaults recovered by the pre-DEK code have field ciphertexts that no longer decrypt with any key; the v1→v2 migration's verification therefore always fails, the vault stays in legacy mode indefinitely and the user is not told. | A repair path (salvage readable fields, report lost ones) needs its own design and owner decision; not in this round. The legacy fallback keeps the DB openable (C1), no data is deleted. | 2026-09-28 |

## Reporting and arbitration

Any change in scope must report the status of **every** convention above: satisfied (with test or code location), or an exception recorded in this file with scope, reason and date. Skipping a convention silently is a violation. If code and this contract disagree, fix the code unless the owner changes the contract.
